# 文案打法库（渠道 × 骨架 × 语气）

> 面向店主与开发者：**"这条文案为什么这么写"要能回答，"下次换个渠道"要能一键换。**
> 灵感来自生成型 skill 的成熟做法（把「怎么写」拆成正交维度 + 预设 + 自动选型），
> 落地成项目里的 `copy_playbook` / `copy_director` / `copy_review` 三层。

---

## 一、为什么要有这一层

补强前，文案能力是「两个员工 + 一段长提示词 + 碰运气出 3 条」：渠道纪律、结构、
禁用词全糊在提示词字符串里。这带来三个具体问题：

1. **不可解释**：给出一条文案，说不清它是"按什么路子写的"，也没法只换渠道重出。
2. **不可复现**：改一个词要动源码；同样的场景两次给的结构差别很大。
3. **不可验收**：合规只靠"再让模型读一遍"，既不能单测，也无法证明它拦住了什么。

参考对象（`baoyu-xhs-images`）之所以稳，是因为它把生成拆成
**12 样式 × 8 布局 × 3 配色 + 预设 + 自动选型**，并把合规与 AI 味写成可执行的自检。
这一层把那套方法论搬到文案上——换的是维度的**内容**，不是形式。

---

## 二、三层结构

```
copy_playbook.py   数据层：渠道 / 骨架 / 语气 / 配方 / 词表的声明 + 规格读取（纯数据）
copy_director.py   导演层：按信号选组合、拼"写法说明"、压"组合摘要"（纯决策）
copy_review.py     检查层：硬规则合规与 AI 味自检、配图方案、交付报告（纯判定）
```

三者都是**纯本地**：不调 AI、不联网、不读库，因此可以单测、可以在无 Key 时给出选型理由。
落笔仍在 `team_domain_copy.generate_copy`。

## 三、三个维度

### 3.1 渠道（发到哪 = 平台硬约束）

| 渠道 | 名字 | 软/硬上限 | 读者状态 | 特有禁忌 |
|---|---|---|---|---|
| `moments` | 朋友圈 | 100 / 220 字 | 老客随口一看 | 活动预告腔、@全体、外链、店名开头 |
| `xiaohongshu` | 小红书正文 | 600 / 1000 字 | 陌生人决定要不要看 | 家人们/宝子们、编造排队盛况、功效暗示 |
| `douyin` | 抖音口播 | 90 / 200 字 | 手指一划的 3 秒 | 点击下方/关注我、标题党承诺 |
| `wechat_group` | 微信群发 | 90 / 180 字 | 群里的老客，扫一眼 | 各位老板/亲们、连发、外链 |
| `signboard` | 招牌短句 | 12 / 20 字 | 路过 2 秒 | 标点堆砌、需要读第二遍的句子 |
| `groupbuy` | 团购说明 | 180 / 300 字 | 正在看商品详情 | 模糊规则、虚构原价、绝对化用语 |
| `reply` | 评价回复 | 100 / 160 字 | 陌生人在看你怎么处理差评 | 怼顾客、模板话、超范围承诺 |

### 3.2 骨架（怎么组织 = 内容结构）

`scene_transplant` 场景移植（让物件开口）· `pain_open` 痛点开场 ·
`listicle` 清单罗列 · `contrast` 对比反转 · `number_hook` 数字钩子 ·
`dialogue` 问答对话 · `counter_intuitive` 反常识

每个骨架带 `shape`（大致形状）、`example`（示例）、`watch`（最容易写坏的地方）。

### 3.3 语气（用什么口气 = 调色板）

`neighbor` 街坊口语 · `promo_bright` 种草活力 · `group_notice` 群通知干脆 ·
`shout` 叫卖直接 · `reply_sincere` 回评诚恳 · `pro_plain` 专业克制

语气只改**口气**，不改结构；就像配色只改颜色、不改渲染规则。

### 3.4 配方（常用组合的缩写）

10 个配方：`moments_daily` / `moments_soft_ad` / `xhs_note` / `xhs_guide` /
`douyin_shout` / `group_notice` / `group_urge` / `board_one_line` /
`reply_sincere` / `review_answer`。

## 四、自动选型（内容信号 → 组合）

`copy_director.select_combo()` 的优先级：

1. **显式参数**（前端/调用方指定了渠道/骨架/语气/配方）；
2. **意图信号**：从上往下第一个命中的赢（如"小红书探店"→ `xhs_note`，
   "有差评要回复"→ `reply_sincere`，"明天闭店"→ `group_notice`）；
3. **业态兜底**：没信号时按业态给（餐饮/饮品→朋友圈日常，零售/生鲜→群通知，摆摊→招牌）；
4. **最常用兜底**：什么都没给 → `moments_daily`。

无论走哪条，都会产出一句**人话理由**（`combo.reason`）进交付报告，例如：

> 从「小红书」判断是小红书·探店笔记的场景。

这就是"可解释"的落点：店主看得懂为什么是这么写的，而不是被告知"AI 觉得这样好"。

## 五、硬检查（合规 + AI 味）

`copy_review.review()` 把能写死的部分做成规则表，命中即报：

| 规则 | 判什么 | 严重度 |
|---|---|---|
| `absolute_terms` | 绝对化用语（最好/第一/全网最低/唯一…） | **fail** |
| `medical_claims` | 医疗功效暗示（治疗/排毒/降血压/减肥…） | **fail** |
| `finance_promises` | 收益承诺（保本/稳赚/无风险…） | **fail** |
| `traffic_fake` | 诱导与虚假流量（集赞/点击下方/排队两小时…） | **fail** |
| `urgency_fake` | 虚假紧迫（最后一天/仅此一次…） | **fail** |
| `channel_banned` | 该渠道特有禁忌（外链、@全体、模板称呼…） | **fail** |
| `length` | 超渠道上限 | 超一点 warn，超 10% fail |
| `ai_slop` | 空话套话（赋能/甄选/匠心/家人们…） | warn |
| `concreteness` | 具体度 = 具体物个数 ÷ 句子数，低于门槛 | warn |
| `action_hint` | 有没有告诉顾客"几点/在哪/多少钱" | warn |
| `generic_tail` | 结尾是不是"期待您的光临" | warn |
| `brand_first` | 第一句是不是店名/括号头 | warn |
| `skeleton_fit` | 选了骨架却没按它的形状写 | warn |
| `too_many_lines` / `exclaim_stack` / `repeat_phrase` | 行数、感叹号、重复短语 | warn |

`verdict` 三态：任一 **fail** → `fail`；只有 warn → `warn`；全过 → `pass`。

### 覆盖边界（已知局限，别当成万能）

判定前会把文本**归一化后再匹配**：NFKC（全角→半角、全角 `＠`）、去空格/标点/emoji
（含不可见的变体选择符）、繁体转简、小写。所以这些变体绕过都拦得住（实测）：

- 拆字与分隔符：`最 好 吃`、`最·好·吃`
- emoji 夹带：`最好❤️吃`
- 繁体：`全網最低價`
- 全角与大小写：`１００％`、`ＹＹＤＳ`

**两类天生拦不住**（属于字面匹配的固有局限，靠 AI 员工的语义复查兜底）：

- **同义替换**：`顶尖`、`首屈一指`、`无与伦比` 表达绝对化，词表里没有就漏；
- **谐音与拼音**：`sī 信我`、`坠好`。

因此规则表只当"低成本的确定性防线"，不替代合规审核员工；报告里的 `verdict` 也不代表法律意见。

> ⚠️ 维护提醒（踩过的坑）：**规则词自己归一化后不能是空串**。
> 招牌渠道的禁忌一度写成「，」「；」两个标点词，归一化后变 `''`，而 `'' in flat` 恒真 →
> 招牌渠道**任何非空文案都被判 fail**，且全量测试全绿（因为没有一条"招牌干净文案"用例）。
> 标点类问题改用"标点堆砌"判定（`punctuation_pileup`），词表里只放**有实义的词**。

> ### ⛔ 一条硬约束：**只标记，不改写**
> 发现违禁词**不会**自动替换正文，只标记 + 给修改方向，由生成方重出或人工决定。
> 理由：静默替换会让人以为已经合规，而替换后的句子往往更糟（"绝不"改成"不"，语义就飘了）。
> 这与 `plain_language` 的术语翻译不同——那层是**翻译**，这层是**合规判定**，
> 判定结果不能偷偷改结论。

## 六、配图方案（文案 + 图，但不生成图）

参考生成型 skill 的"封面 → 内容 → 结尾"三段式，`build_image_plan()` 给每张图：
**画面描述、图上文字、比例、可直接喂给绘图模型的提示词**。

小店的现实是"拿手机拍一张"，所以默认按渠道给 1~3 张：**朋友圈 / 群发 / 招牌 = 1 张**，
**小红书 / 抖音 / 团购 = 3 张**（封面把"事"放进画面，图上文字只放一个钩子），
**评价回复不配图**（配了反而像模板回复）。
所有分支都返回同样的键（含 `text_hint`），前端不必做分支判断。
项目里不做图片生成，这里只产出可执行的拍摄/排版说明。

## 七、接口

`POST /api/insights`（`scene: "copy"`）新增顶层字段：**除 `biz_type`/`return_report` 外都走 `Literal`**，
非法值在请求期 422。

| 字段 | 取值 | 说明 |
|---|---|---|
| `channel` | 7 个渠道或空 | 不传=按信号自动选 |
| `skeleton` | 7 个骨架或空 | 不传=按配方/信号/该渠道常规写法 |
| `tone` | 6 个语气或空 | 同上 |
| `recipe` | 10 个配方或空 | 传了就等于一键选好渠道+骨架+语气 |
| `biz_type` | 开放取值（业态，`str`） | 只用于兜底选型；业态本来就不该被枚举钉死 |
| `return_report` | `bool` | true=额外返回交付报告 |

响应在原有 `text` / `variants` / `team` / `gene_id` 之外增加：`combo`（渠道/骨架/语气/配方 + 人话理由）、
`verdict`（pass/warn/fail），以及 `report`（含逐条检查、诊断数据、配图方案）。

**向后兼容**：老的 `payload`-only 调用完全不变；`team`（含 `employees`/`adopted`/`gene_id`）
仍按原样返回。`variants` 的准确含义是"**主文案 + 模型给的全部稿**"（融合稿不在模型稿里时会多一条），
不是"正好等于模型稿数"。

## 八、改这一层时注意什么

1. **取值只加不改**：`CHANNELS`/`SKELETONS`/`TONES`/`RECIPES` 是唯一真源，
   `schemas.py` 的 Literal 与之一致，由 `tests/test_copy_playbook.py` 回归（铁律5）。
2. **加渠道就补齐四件事**：`scene_hint`（读者状态）、`structure`（结构纪律）、
   `avoid`（渠道禁忌）、`soft/hard_max`（字数），否则注册表自检会红。
3. **加词表要想清楚严重度**：会造成法律风险（广告法/医疗/收益承诺）的进 `fail`，
   只是"读起来假"的进 `warn` —— 严重度决定店主会不会被拦住。
4. **阈值进 config**：字数上限与具体度门槛都在 `config.COPY_*`；
   检查时取「config 阈值」与「打法库声明」里更严的那个，避免两处口径打架。
   报告里的 `combo.limits` 与 `reviews[].diagnostics.limit` 都给**实际生效值**（同一个函数算），
   `config` 配 ≤ 0 视为"没配"（`or` 会把 0 当假值吞掉，实测踩过）。
5. **降级文案不许动**：无 Key 时的文本有既有测试逐字断言，改它会连带炸掉演示动线。
