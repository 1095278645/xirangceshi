# 专项优化：AI 掌柜技能架构 + 用户语言降维

> 针对两个核心方向：①AI 侧深入统合信息、以 skill 能力架构为重点；②用户侧减少专业词汇、入口小但挖掘深。
> 基于现有代码实测（`team.py` / `team_domains.py` / `evolution.py` / `heartbeat.py` / `routers/registry.py`），给出**不改架构骨架、只加薄层**的落地方案。

---

## 第一部分：AI 侧——把掌柜从"功能调用者"升级为"技能组织者"

### 现状诊断

你已有的架构其实非常接近"skill 体系"：

| 已有组件 | 现在是什么 | 缺什么 |
|---------|-----------|--------|
| `TEAM_DOMAINS`（team_domains.py） | 声明式业务域注册表 | 只有"域"，没有"技能卡片"级别的元数据 |
| `_run_team()` | 多员工竞争 → 掌柜裁决融合 | 员工不能跨域协作，域与域之间是孤岛 |
| `heartbeat.py` 每日复盘 | 定时触发五伙计合议 | 触发条件写死在定时器里，不能按"事件"激活 |
| `evolution.py` 进化引擎 | 基因选择 → 蒸馏 → 晋升 | 只跟踪"提示词策略"的进化，不跟踪"技能"本身的成熟度 |
| `shop_snapshot.py` | 全店事实快照 | 快照只给复盘用，其他域不能按需取用 |

**核心洞察：你的架构已经有骨架，缺的是一层"胶水"——把散落的组件粘成"一个会主动干活的掌柜"。**

### 优化 1：统一店铺上下文（Store Brain）

#### 问题

现在每个业务域自己查自己的数据：
- 复盘域查 `shop_snapshot`
- 单店诊断查 `store.py` + `db.py`
- 熟客记忆查 `db_customers.py`
- 税务查 `tax.py`

如果要让掌柜做到"深入统合信息"，它需要一个**统一的认知层**——像人脑一样，不是每次想事情都要去翻不同的柜子。

#### 方案：新增 `store_brain.py`

```python
# server/store_brain.py — 店铺统一认知层
"""所有 skill 从这里取上下文，不直接查 DB。
好处：skill 之间看到的是同一份"事实"，不会出现财务域和库存域对同一笔账理解不同的情况。"""

def build_context(shop_id: str) -> dict:
    """汇聚全店事实为一个 dict，skill 按需取用"""
    return {
        "profile": ...,       # 店档案（业态/面积/成本结构）
        "cash_flow": ...,     # 近 30 天收支 + 趋势
        "breakeven": ...,     # 保本线 + 当前差距
        "customers": ...,     # 熟客频次 + 沉睡名单 + 消费偏好
        "inventory": ...,     # 库存天数 + 缺货预警
        "tax_status": ...,    # 本期应报税 + 临界提醒
        "supply_chain": ...,  # 进货频率 + 票据完整率
        "corrections": ...,   # 近期纠错（AI 学到了什么）
        "learnings": ...,     # evolution 已晋升的经验
    }
```

#### 落地方式

1. 在 `shop_snapshot.py` 基础上扩展，增加 `customers / inventory / tax_status / supply_chain` 维度
2. `heartbeat.py` 的五伙计改为从 `store_brain.build_context()` 取数据（而非各自查）
3. 所有 `team_domain_*.py` 的 `_run_team()` 调用点统一传入 `context` 参数
4. **不改 DB 层**，只在编排层加一个聚合函数

#### 效果

- 财务伙计可以看到库存数据 → "酱油只够 3 天了，要不要和进货一起下单？"
- 熟客伙计可以看到现金流 → "陈伯欠了 200 块 14 天，但你现金充裕，不急催"
- 掌柜裁决时拥有全维度事实 → 裁决质量从"盲人摸象"变为"全景判断"

### 优化 2：技能卡片化（Skill as Card）

#### 问题

现在 `TEAM_DOMAINS` 是"域注册表"（copy / store / review），但"技能"的概念比"域"更细。比如：
- "发现进货缺票据"是一个技能
- "发现熟客流失"是一个技能
- "发现现金低于警戒线"是一个技能

这些目前散落在复盘域的提示词里，没有被显式建模。

#### 方案：扩展 `TEAM_DOMAINS` 的元数据

```python
TEAM_DOMAINS = {
    "review": {
        "enabled": True,
        "module": "team_domain_review",
        # —— 新增：技能卡片 ——
        "skills": [
            {
                "id": "detect_missing_invoices",
                "name": "抓漏票",
                "trigger": "monthly_purchase > 5000 and invoice_rate < 0.5",
                "context": ["supply_chain", "tax_status"],
                "entry_question": "本月进货 {amount} 元，票据齐了吗？",  # 用户看到的问题
                "professional_name": "进项票据完整率检查",  # 内部专业名（不展示给用户）
                "severity": "high",
            },
            {
                "id": "detect_customer_churn",
                "name": "揪沉睡熟客",
                "trigger": "customer_inactive_days >= 14",
                "context": ["customers"],
                "entry_question": "{name} {days} 天没来了，要不要打个电话？",
                "professional_name": "熟客流失预警",
                "severity": "medium",
            },
            {
                "id": "detect_cash_shortfall",
                "name": "盯现金",
                "trigger": "cash_runway_months < 2",
                "context": ["cash_flow", "breakeven"],
                "entry_question": "手里的钱还能撑 {months} 个月，要不要省着点花？",
                "professional_name": "现金跑道预警",
                "severity": "high",
            },
        ],
    },
}
```

#### 关键设计

- **`trigger`**：用简单的条件表达式，不引入新依赖
- **`entry_question`**：这是用户看到的**唯一一句话**——专业术语为零
- **`professional_name`**：仅内部使用，答辩时可以说"我们内部叫 X，但用户只需要理解 Y"
- **`severity`**：决定展示优先级——高严重度的技能先出

#### 落地方式

1. 在 `TEAM_DOMAINS` 的每个域下加 `skills` 列表（纯数据，不改逻辑）
2. 新增一个 `evaluate_triggers(context)` 函数，遍历所有 skill 的 trigger 条件
3. 命中的 skill 按严重度排序，取 top 1-2 作为掌柜的"今日盯什么"

### 优化 3：主动触发引擎（从"被调用"到"主动干活"）

#### 问题

目前 heartbeat 只在固定时间（每天一次）触发。但有些事等不到每天：
- 刚记了一笔大额进货 → 应该立刻提醒票据
- 现金刚跌破警戒线 → 应该当天提醒
- 熟客刚好第 14 天没来 → 应该当天提醒

#### 方案：在记账/收款时触发"即时技能检查"

```python
# 在 db_ledger.py 或 routers/voice.py 的记账成功回调中：
def after_ledger_created(entry):
    context = store_brain.build_context(current_shop_id)
    triggered = evaluate_triggers(context)
    for skill in triggered:
        if skill["severity"] == "high":
            notifications.push(shopkeeper_message(skill))
```

#### 落地方式

1. 在 `main.py` 的后台任务中，除了每 6 小时的 heartbeat，增加一个**事件驱动的轻量检查**
2. 不需要新框架——FastAPI 的 `BackgroundTasks` 就够了
3. 触发频率控制：同一 skill 每天最多触发 1 次，防止打扰

#### 效果

掌柜从"每天晚上复盘一次"变成"随时在岗，有事立刻叫你"——这才是"雇员"和"工具"的真正区别。

### 优化 4：技能成熟度与置信度

#### 问题

进化引擎目前跟踪的是"提示词策略"（哪个员工的话被采纳）。但用户视角看，更重要的是"这个技能靠不靠谱"。

#### 方案：给每个 skill 挂一个置信度分数

```python
# 在 evolution.py 的 outcome 记录中增加 skill_id 维度
def record_skill_outcome(skill_id: str, success: bool, user_feedback: str | None = None):
    """success: 用户是否看了/点了/采纳了这个技能的建议"""
    # 累计到 db_evolution，按 skill_id 聚合
    # 置信度 = 近 30 天成功率
    # 低于 30% 的技能自动降级为"低频触发"，减少打扰
```

#### 技能生命周期

```
新建 → 学习期（只展示给少数用户，收集反馈）
     → 成长期（触发条件逐步放开）
     → 成熟期（自动触发，高置信度）
     → 休眠（用户忽略率高，降频或下线）
```

#### 落地方式

1. 在 `db_evolution.py` 的表中加一列 `skill_id`
2. 在前端，用户看完掌柜建议后加一个"有用/没用"轻量反馈
3. `evaluate_triggers()` 根据置信度调整是否触发

### 优化 5：跨技能联动（掌柜的"直觉"）

#### 问题

单一技能看到的是单维度。但掌柜的真正价值是**把多个信号连起来看到人看不到的东西**。

#### 举例

| 信号 A | 信号 B | 联动洞察（掌柜的"直觉"） |
|--------|--------|----------------------|
| 进货占收入比偏高 | 现金跑道 < 3 个月 | "你是不是在囤货？现金不多了，先别大量进货" |
| 熟客流失率上升 | 客单价下降 | "老顾客在流失且新客客单低——试试老带新活动" |
| 毛利率稳定 | 库存周转天数增加 | "利润率没变但东西卖得慢了——可能是这条街新开了竞品" |

#### 方案

在 `_decide()`（掌柜裁决函数）中，除了融合员工候选，还传入当前命中的技能列表：

```python
def _decide(task_desc, cands, triggered_skills=None, ...):
    # 掌柜提示词中追加：
    # "你今天同时激活了以下技能：{skill_names}。
    #  如果这些信号之间有关联，优先指出关联——这是你比单个伙计更有价值的地方。"
```

#### 效果

评委听到这个设计会立刻理解——**这不是 N 个独立功能的堆叠，而是一个能做跨域推理的"掌柜大脑"**。

## 第二部分：用户侧——"一句话入口 + 三层深度"

### 现状诊断

| 做得好的 | 还可以更好的 |
|---------|------------|
| 语音输入已经是零门槛 | 输出中仍有"保本点""应收账款""进项税"等术语 |
| 朋友圈文案是口语化 | 单店诊断的输出虽然有建议，但数字术语仍偏专业 |
| 复盘有"大白话"基调 | 没有系统性的"术语→人话"映射层，靠每个提示词各自保证 |

**核心洞察：语言降维不应该是每个提示词里的"附带要求"，而应该是一个独立的、系统性的输出层。**

### 优化 6：专业词汇翻译层（Plain Language Layer）

#### 方案：新建 `plain_language.py`

```python
# server/plain_language.py — 专业术语 → 大白话 映射表
"""所有面向用户的 AI 输出，在返回前端之前都过这一层。
类似国际化的 i18n，但这里是"专业知识本地化"——把会计语言翻译成生活语言。"""

TERM_MAP = {
    "保本点": "每天至少要卖多少钱才不亏",
    "保本线": "每天至少要卖多少钱才不亏",
    "毛利率": "每卖 100 块，赚多少",
    "应收账款": "别人还欠你的钱",
    "应付账款": "你还欠别人的钱",
    "进项税": "你买东西时可以抵的税",
    "销项税": "你卖东西要交的税",
    "现金跑道": "手里的钱还能撑几个月",
    "回本周期": "投的钱多久能赚回来",
    "库存周转天数": "货架上的东西多久能卖完",
    "客单价": "每个客人平均花多少钱",
    "复购率": "客人会不会再来",
    "经营性现金流": "卖东西收到手的钱，减去花出去的钱",
}

def translate(text: str) -> str:
    """按词组长度降序替换，避免短词误替换长词"""
    for term in sorted(TERM_MAP, key=len, reverse=True):
        if term in text:
            text = text.replace(term, TERM_MAP[term])
    return text
```

#### 落地方式

1. 新建文件，纯函数，零依赖
2. 在 `team_domains._run_team()` 返回最终文本前调用 `plain_language.translate()`
3. 在 `heartbeat.generate_daily_review()` 返回前调用
4. 加一个单元测试：输入含术语的文本，断言输出不含术语

#### 效果

所有 AI 输出的专业术语**强制**被翻译，不依赖提示词的"自觉性"。

### 优化 7：渐进式披露（三层深度）

#### 问题

"入口小但挖掘深"的矛盾在于：太浅则没有价值，太深则吓跑用户。答案是**分层展示**。

#### 方案：每个输出分三层

```json
{
  "layer1_summary": "李婶，今天赚了 347 块，但有个事要盯：进货 8025 块没票据。",
  "layer2_detail": "进货占了这个月收入的 38%，偏高。如果没票据，月底算税时抵不了，可能多交几百块。建议明天找供应商把票要回来。",
  "layer3_analysis": {
    "breakeven": {"daily_target": 340, "actual_today": 580, "status": "above"},
    "invoice_rate": {"total_purchase": 8025, "with_invoice": 0, "rate": 0},
    "action_items": ["催票据", "核对入库单", "微信上问供应商能否补开"]
  }
}
```

| 层 | 用户看到什么 | 谁会看 |
|----|------------|--------|
| 第一层 | 一句话结论 + 一个行动建议 | 90% 的用户（李婶） |
| 第二层 | 点开后：数字解释 + 为什么重要 | 20% 的用户（李婶的儿子） |
| 第三层 | 再点开：完整分析数据 + 图表 | 5% 的用户（会计/银行） |

#### 落地方式

1. 在 `heartbeat.py` 的复盘结果中，除了全文，额外输出一个 `layer1_summary` 字段
2. 小程序首页只展示 `layer1_summary`，下方放"展开看细节"
3. 第三层可以复用现有的报表页面

#### 效果

- 李婶打开 app 只看到一句话 → **零认知负担**
- 她儿子想深入了解可以点开 → **有深度但不强迫**
- 银行/会计要看完整数据 → **有专业底层**

### 优化 8：问题式界面（不是菜单，是掌柜问你话）

#### 问题

传统 app 的信息架构是"功能菜单"：记账 | 熟客 | 报表 | 税务 | 库存……用户要自己知道"我该用哪个功能"。

但对于不懂财务的李婶，**她不知道自己需要什么功能**。她只知道"我有个问题想问"。

#### 方案：首页从"功能入口"改为"掌柜的问题"

**现在的首页（推测）：**
```
┌────────────────────────┐
│ [语音记账按钮]          │
│ ┌────┐ ┌────┐ ┌────┐ │
│ │记账│ │熟客│ │报表│ │
│ └────┘ └────┘ └────┘ │
│ ┌────┐ ┌────┐ ┌────┐ │
│ │税务│ │库存│ │诊断│ │
│ └────┘ └────┘ └────┘ │
└────────────────────────┘
```

**优化后的首页：**
```
┌────────────────────────┐
│ 🔍 [按住说话，记一笔]    │
│                        │
│ 📋 掌柜今天提醒你：      │
│                        │
│ ① 进货 8025 元没票据，  │
│    明天记得要回来。      │
│    [展开看怎么催 →]      │
│                        │
│ ② 陈伯 14 天没来了，    │
│    打个电话？            │
│    [一键拨号 →]          │
│                        │
│ ③ 今天卖了 580 块，     │
│    保本线以上，不错。    │
│    [看这个月的 →]        │
└────────────────────────┘
```

#### 关键设计

- **不出现功能名**——不叫"财务报表"，叫"看这个月的"
- **不出现专业词**——不叫"库存周转预警"，叫"酱油还能用 3 天"
- **每个提醒带一个行动入口**——不是看完就走，是"现在就做"

#### 落地方式

1. 首页 `pages/index/index.wxml` 改为以"掌柜提醒卡片"为主视图
2. 语音记账按钮保留（这是核心入口，不能藏起来）
3. 底部 tabbar 可以保留，但从 5 个减到 3 个（首页 / 记账 / 我的）
4. 提醒卡片的数据来源就是优化 3 的"主动触发引擎"

### 优化 9："所以呢？"过滤器（So-What Filter）

#### 问题

AI 输出的常见问题是"分析了很多，但用户不知道该干什么"。比如：

> ~~"您的毛利率为 42%，低于行业均值 48%，建议优化成本结构。"~~

李婶看完的反应："所以呢？我该干嘛？"

#### 方案：所有输出必须通过"所以呢？"测试

在掌柜裁决的提示词中追加一条硬性规则：

```
你必须回答以下三个问题，缺一不可：
1. 发生了什么？（用数字，但不超过 2 个）
2. 为什么我在意？（跟李婶的钱或时间直接相关）
3. 我该做什么？（明天就能动手，具体到"找谁、说什么"）
```

#### 改造示例

| 改造前 | 改造后 |
|--------|--------|
| "您的毛利率为 42%，低于行业均值 48%" | "你每卖 100 块赚 42 块，隔壁早餐铺能赚 48 块。差的那 6 块主要是面粉进价贵了——换个批发市场，一个月能省 800 块。" |
| "建议优化库存周转率" | "货架上的酱油囤了 3 个月的量，先别再进了，用完再买。现金留着周转。" |
| "应收账款账龄较长" | "老王欠你 200 块快 3 周了。找个理由打个电话——'新到的咸菜给你留一袋'——比直接催债好开口。" |

#### 落地方式

1. 在 `_decide()` 掌柜提示词中追加"三问规则"
2. 在 `plain_language.py` 的 `translate()` 后追加 `so_what_check()`——如果输出中没有行动建议，自动补一句"你要不要……"

### 优化 10：输出口径统一（所有域一个声音）

#### 问题

现在不同域的输出风格可能不一致：朋友圈文案域可能很活泼，诊断域可能很严肃，税务域可能很官方。对用户来说，这是"不同的 app"而不是"同一个掌柜"。

#### 方案：定义统一的"掌柜人格"

```python
# server/shopkeeper_persona.py — 掌柜人格统一定义
PERSONA_RULES = """
你是李婶店里的老掌柜，说话规矩：
- 称呼：叫"老板"或"李婶"，不叫"用户"或"您"
- 语气：像街坊聊天，不像客服，更不像教科书
- 数字：每次最多提 2 个数字，超过的放进"展开看"
- 行动：每个结论后面必须跟一个"明天就能做"的事
- 术语：说"欠你的钱"不说"应收账款"，说"至少卖多少"不说"保本点"
- 情感：心疼钱但不吓唬人；有问题直说，但最后一定给一条出路
- 篇幅：第一句话不超过 30 个字，总体不超过 3 句话
"""
```

#### 落地方式

1. 新建 `shopkeeper_persona.py`，定义人格常量
2. 所有 `team_domain_*.py` 的员工 system prompt 中追加 `PERSONA_RULES`
3. 降级函数（无 Key 模式）也使用同一套口径

#### 效果

不管用户在哪个页面，看到的都是同一个"人"在说话——**这就是"掌柜角色"而不是"功能集合"**。
