# AI 掌柜能力补强 · 钱学森系统工程视角的评审与路线图

> 本文不是功能罗列，而是一份**总体设计视角的评审**：先把项目当系统看，再判断
> 缺的是哪一层，最后给出可验收的补强动作与路线图。
> 方法取自钱学森的系统工程与系统科学论述（开放的复杂巨系统、从定性到定量的综合集成法、
> 总体设计部、归零制度、技术科学三层次），适用范围与不确定性在文末「诚实边界」里写明。

## 一、系统定位：这是一台什么机器

用钱学森的话说，**一家小微实体店的经营，是一个开放的复杂巨系统**：

- **开放**：店与外部环境持续交换——供应商、熟客、平台收款、税务、房租、天气与商圈。
- **复杂**：子系统种类多且互相耦合——钱账、人（熟客）、货（库存）、票税、异常，
  一个动作会牵动另外几个（赊账压现金 → 进货减少 → 缺货 → 熟客流失）。
- **巨量**：单看要素数量不大（一家店几十个熟客、几百种货），但**状态组合**与**时间序列**
  很大：3200 笔流水、按天按月的口径、跨月跨季的税期。

因此这个项目的正确评价标准**不是"模型多聪明"，而是"这台经营机器能不能长期稳定运行"**。
这也是为什么仓库里的铁律写着"数据默认留在本地""危险操作必须确认""变更必过验收"——
它们不是洁癖，而是**工程系统的可靠性约束**。

### 1.1 现状盘点（当作总体设计的第一张图）

| 层次 | 项目已有的东西 | 判断 |
|---|---|---|
| 感知 | 语音记账、收款即入账、账单同步、`shop_snapshot` 汇总全店事实 | **扎实**：事实进得来，且"没数据"也如实说出来 |
| 记忆 | `domain_context`（按域隔离的经营记忆）、熟客档案与记忆点、单店档案 | **可用但平铺**：只有键值，没有关系、没有来源、没有版本 |
| 决策 | 多 agent 竞争 → 掌柜裁决（`team_domains`）、技能卡片三层输出、质量门禁（`ai_quality`） | **有骨架**：员工职责不重叠、掌柜必须取舍、结论要证据 |
| 行动 | 每日复盘、熟客提醒自动送达与重试、主动触达多通道 | **闭环已成**：不是"给了建议"，而是"被送达、被记录、没送到会重来" |
| 反馈 | 采纳归因、复盘有用/没用、进化层（基因/蒸馏/抑制，默认关闭） | **信号稀薄**：只有网页端上报，小样本不收敛（README 已诚实标注） |

**结论：五段闭环里，"感知—决策—行动"已经打通，"记忆"与"反馈"是短板。**

## 二、诊断：短板到底缺什么

参考图给出了一条 2020→2026 的能力演进线：**找得到 → 看得懂 → 管得住**。
把这把尺子量到本项目上：

| 参考图阶段 | 本项目对应物 | 差距（本体缺什么） |
|---|---|---|
| **找得到**（Vector RAG / 相似度检索） | `domain_context`、AI 缓存、`insight_index`（≤20 行极简索引） | 检索是**按 key 取**的，没有"按语义找"的统一入口；跨域问题（"这个熟客和哪些货、哪些票有关"）无从表达 |
| **看得懂**（GraphRAG / 关系与全局理解） | **几乎没有**：熟客/商品/供应商/发票/流水分散在七张表里，`shop_snapshot` 把它们**拍平成文本** | 没有显式的关系边，于是"全局理解"只能靠提示词里堆文本，员工看到的是一串事实而不是一张网 |
| **增量合并**（LightRAG） | 进化层有经验去重与基因统计；`agent_capsules` 只增不减（有 `prune_evolution_data`） | 知识的合并粒度是"基因/胶囊"，**不是"结论"**；结论级别的版本、覆盖、回收都没有 |
| **持续编撰**（LLM Wiki） | 提示词散落在 `ai_prompts.py` / `shopkeeper_persona.py` / 技能卡片 | 知识没有"资产"身份：**谁写的、依据什么、什么时候被推翻**，查不到 |
| **管得住**（OKF + Git：版本/评审/追踪/回滚） | `safe_io` 原子写、`backup` 一致性快照、`agent_events` 审计 | 保护的是**数据文件**，不是**知识**；知识改动没有版本、没有回滚、没有来源追溯 |

### 2.1 一句话诊断

> **这台机器"能干活"，但它的知识还不成资产。**
> 掌柜说出的每一句结论，都还是一次性的文本：
> 写下去就散落在 `domain_context`、提示词、缓存和员工输出里，
> 既回答不了"凭什么这么说"，也回答不了"这个说法现在还算不算数"。

用钱学森的概念对照，这恰好是**技术科学层次缺了一层**：
基础科学（数据与算法）有了、工程技术（功能与界面）很全，
但中间那层"把经验沉淀为可用知识、并保证它长期有效"的**桥梁**没建。

## 三、补强方案：两个新层次（本次落地）

### 3.1 知识资产治理层（补「管得住」）

**核心命题：知识不是一段文本，而是一件资产。** 因此它必须具备四个属性——缺一个就不算资产：

| 属性 | 落地点 | 对应参考图 |
|---|---|---|
| **来源可溯** | 每件资产带 `source_kind` / `source_ref` / `evidence`；`/api/knowledge/assets/{id}/sources` 一路点到原始单据 | LLM Wiki「持续编撰」+「来源分层」 |
| **版本与状态** | `register_asset` 按内容哈希判定：同内容幂等不重复、内容变了则旧版标 `superseded`、新版 `version+1`，`valid_from/valid_to/superseded_by` 全留痕 | OKF + Git「版本/追踪/回滚」 |
| **运行期核验** | 资产带 `volatility`（stable / slow / volatile）；volatile 资产在读取时回到真值上核验，对不上的标记为"待复核"（`verify_ok=0` + 人话原因），**不许继续当结论用**；新建的 volatile 资产从"未核验"起步 | 图末「当前动态事实回到运行时核验」 |
| **可打包审计** | `/api/knowledge/bundle` 把资产 + 关系导成带格式版本号的 JSON（走 `safe_io` 原子写、落 `data/`） | OKF「文件包装与交换」 |

关键设计取舍：**稳定资产与动态事实分层**。
技能卡片（"进货没票""临期货物"）是判定规则，稳定；"今天流水 580 元"是动态事实，会过期。
把两者混成一堆，就会出现"看起来有知识、其实全是过期数字"的假象——
这正是参考图把"知识文件"与"缓存加速层"分开的原因。

### 3.2 跨域关系索引层（补「看得懂」）

**核心命题：全局理解不是把文本堆在一起，而是把实体连成网，并且每条边都能回查。**

- 实体：熟客 / 商品 / 供应商 / 发票 / 流水 / 赊账（对应的都是**已有表**里的真实记录）。
- 边：买过、卖出在、由供货、开票对象、我欠他/他欠我、关联流水（退货红冲）。
  每条边的 `evidence` 是原始事实字符串（如"交易#1234 2026-10-01 12.00 元 肉包"）。
- 增量合并（LightRAG 思想）：重算抽取 → upsert（内容未变只刷新 `last_seen`）
  → 这次没再被证实但原本有效的边**软删**（`active=0` + `valid_to`，保留可回溯）。
- 体检（`graph_health`）：孤儿边、悬空对象、重复键、陈旧边——
  **关系索引自己也要能被核验**，否则它就是新的"看不见的脏数据"。
- 检索：`neighbors`（BFS，1~3 跳）与 `find_paths`（最短路径），
  用来回答"这条结论是怎么串起来的"。

### 3.3 为什么是这两层，而不是加更多 agent

钱学森的**总体设计部**原则：总体部不替子系统干活，它管**接口与整体最优**。
本项目已经有七个岗位、三个多 agent 域（文案/单店/复盘），
再加员工只会让候选更趋同——README 自己都写了"五位伙计职责不重叠，否则竞争白设"。

真正的瓶颈不在"再多一个岗位"，而在**岗位之间共享的那张网**：
熟客管家知道陈伯两周没来，采买师傅知道肉快没了，税务管事知道票没回来——
但他们不知道**这三件事是同一件事**（陈伯常买肉包，肉卖不动 → 陈伯可能也不来了）。
关系索引层就是把这三条线连起来的那张网；
知识资产层是让"连出来的结论"可追溯、可回收的那本账。

## 四、从定性到定量的综合集成：闭环怎么验

钱学森的方法论要求"专家体系 + 数据体系 + 计算机体系"综合集成，并且**每一步都要能量出来**。
本次补强给每一步配了可观测的量：

| 环节 | 补强前 | 补强后 | 观测点 |
|---|---|---|---|
| 感知 | 事实拍平成快照文本 | 快照 + 关系边 | `GET /api/relations/summary`（有效边/关系类型/体检） |
| 记忆 | 键值上下文，来历不明 | 资产台账（来源/版本/状态） | `GET /api/knowledge/summary` |
| 决策 | 掌柜裁决 + 证据 | 同一裁决，但证据登记为资产、可逐条溯源 | `GET /api/heartbeat` 的 `knowledge` 块 |
| 行动 | 送达与重试闭环 | 不变（不动已完成的东西） | `notification_logs` |
| 反馈 | 采纳归因（稀薄） | 资产版本演进 + `stale` 计数 | `assets_stale` / `by_state` |
| 治理 | 无 | 运行期核验 + 知识包导出 | `POST /api/knowledge/verify`、`POST /api/knowledge/bundle` |

**归零制度**（质量问题追根溯源）在软件里的对应物是"每个结论必须能回答三个问题"：
① 依据哪条原始事实？② 什么时候被谁复核过？③ 现在还算不算数？
本次补强的三个接口（`sources` / `verify` / `bundle`）就是把这三问变成可点的按钮。

## 五、路线图（分三步，每步都可独立验收）

### 第一步（本次已做）：把知识变成资产
- 建 `knowledge_assets` 表 + 状态机（draft/active/superseded/retired）+ 内容哈希幂等；
- 复盘产出自动登记为资产（结论 / 命中技能 / 原始事实 / 采纳归因）；
- 运行期核验 + 知识包导出；资产台账页与复盘卡的"结论依据"入口。

### 第二步（下一步，未做）：让关系进入决策
- 把 `neighbors` / `find_paths` 的结果**注入**复盘与单店诊断的上下文
  （现在员工只看平铺事实，看不到"谁和谁有关"）；
- 给关系边加"时效"：交易类边随月份衰减，熟客流失边随回访复活；
- 用关系图做一次真正的跨域判断（如"陈伯不来 → 哪几样货会掉量"），
  并在演示动线里给出可复现的例子。

### 第三步（更远，未做）：反馈信号变厚
- 接通多端采纳上报（现在只有网页端），把 `assets_stale` / 采纳率做成种子，
  再考虑打开进化层（`SHOP_ENABLE_EVOLUTION=1`）；
- 在资产层上做"知识评审"：候选知识必须过证据门（有多少条原始事实支撑）
  与基准门（`eval_ai_parse.py --compare`）才能从 draft 转 active。

**顺序不能颠倒**：第二步依赖第一步的资产身份，第三步依赖前两步的真实样本。
这与钱学森强调的"有计划、有层次地推进"是一致的——
当年搞两弹一星，也是先解决"有"，再解决"准"，最后才谈"体系化"。

## 六、诚实边界（避免评审追问翻车）

1. **一次补强不可能让系统"自己进化"**。本次交付的是**治理能力**（可追溯、可核验、可回滚），
   不是智能提升。进化层仍然默认关闭，理由见 README 与 `deliverables/进化能力研究与优化方案.md`。
2. **关系索引的粒度和覆盖面受数据质量制约**：熟客没建档、商品没登记、发票没录，
   对应的边就不存在——**"没有边"本身是结论（这块经营动作没记），不是缺陷掩盖**。
   抽取有扫描上限（`KNOWLEDGE_EDGE_SCAN_LIMIT`），演示库 3000+ 笔流水不会全量重算。
3. **运行期核验只能验"能回到真值的量"**（流水、库存、票额、现金跑道等）。
   语义判断（"该不该涨价"）无法自动核验，只能靠证据链与人工复核，
   所以它们的 `volatility` 是 `slow`/`stable`，不参与自动核验。
4. **参考图是行业演进的一个抽象**，不是公认标准；本文把它当尺子用，
   而不是当权威结论引用。
5. **本文的钱学森视角是方法借用**：用其系统工程的框架组织问题，
   不复述、不虚构他未发表过的具体论断。
6. **知识层的保留期只做了半步**：关系边（软删后过保留期物理清理）与知识包导出文件
   已挂进 `main._backup_loop` 定期清理；但**知识资产本体仍无保留期**（只增不减，
   约 3~18 行/天）。上线前应把历史版本清理一起挂上去（参照
   `db_evolution_audit.prune_evolution_data` 的现成做法）。
7. **文件是数据目录里唯一需要按需清理的东西**：导出的知识包带时间戳、每次一份；
   已在 `config.KNOWLEDGE_BUNDLE_KEEP_DAYS`（默认 30 天）内有清理，但目录仍会随
   演示频率增长（测试跑一次也会落一份），演示机需要偶尔手动清空 `server/data/knowledge/`。
